# PR51 → PR54 → Raft timeout：问题梳理

当前状态：组合版一小时压力测试及全部状态/重启核验已经通过。随后按真实业务删除接口补充的迁移回归发现了删除位置漏写问题，已修复并通过回归；包含该修复的最终二进制已通过加强后的业务并发和四类故障恢复验收，最后的独立混合负载及恢复/重启复测也已通过。PR54 保持原样；新的 IM 与后端 PR 配套使用，见 PR 关联链接。

## 原来的目标在哪些环节被偏离了

| 环节 | 实际解决了什么 | 缺口或偏离 |
|---|---|---|
| PR51（回移 PR50，不是 PR54 的直接祖先） | 按 Slot 加锁、同步 group commit、清理异步提交，并修复非 leader 静默丢提案却报成功 | 异步成功只到 leader 接纳；其说明已明确未解决多节点高并发超时和清理积压，不能扩大为持久化完成或旧移除/新加入顺序保证 |
| PR54 | 持久化意图、回执、目标会话生命周期、反向关系、恢复进度 | 把完整的源分区→目标分区→源分区完成过程放回 5 秒请求路径；多次落盘和串行等待放大尾延迟 |
| 仅验证超时后能恢复 | 证明队列可继续工作，没有在这些案例中永久卡死 | 用户已经收到失败，不能把后续恢复算作请求成功 |
| 只修 IM 内部 | 能重试 IM 已收到的意图 | 无法补出业务从未发送成功的请求，也不知道业务在丢回复后撤销了 SQL 数据 |
| 只做失败后的补偿队列或重试增删动作 | 覆盖部分普通失败 | SQL 提交后、入队前崩溃仍会漏任务；旧踢人重试可能覆盖后来的重新加入 |

PR51 有实际的存储优化和异步路由正确性修复，应继续保留。偏差在于如果把当时短测和“leader 已接纳”当成两个最终目标都完成，就超出了 PR51 自己声明的边界。

PR54 的持久化机制应保留，不能简单回退为“提交给 leader 就返回成功”。真正需要同时修的是同步执行的存储成本，以及 SQL→IM 之间的可靠边界。

## 证据说明了什么

相同的本地混合负载映射为：378 频道、25 用户、225 初始订阅关系，42 路成员增删、42 路消息、16 路元数据更新；IM 限制 2 CPU/4 GiB，原有 5 秒期限，同一操作 ID 重试。原截图的原始脚本不可得，因此不能声称脚本逐字一致。

PR54 基线约 10 分钟有 327 次 HTTP 失败、253 次 Slot 超时。第 6 版短测曾零失败，但一小时出现 9 次失败、4 次 Slot 超时。第 7 版约 10 分钟仍有 1 次失败。失败均恢复，重启前后成员、会话和消息核对通过；这说明恢复机制有效，同时说明延迟目标还没有过关。

失败时不是再次磁盘满：第 7 版现场约 2.4 GiB 内存，无 OOM、无 CPU 限流，磁盘剩余超过 350 GiB；多个 WAL 同时等待 fdatasync，Pebble publish/Sync 等待突出。可以定位到落盘等待，但不能据此断言是某种 SSD 硬件故障或垃圾回收。

Raft apply 超时表示本次等待没有在期限内完成，并不等于已提交日志被撤销或分区永久卡死。已提交操作仍可能继续执行，所以不能把“调用报错”当作“IM 没发生修改”。此前的一小时失败和后续候选失败均能恢复，但客户端已经收到的失败仍要计入。还发现一个独立的提前失败来源：目标提案要求至少剩余 2 秒预算，实际在原 5 秒期限到达前就退出；删除这个猜测性限制只是在使用原有预算，并没有延长超时。

业务故障注入另外证实了两个独立缺口：

- IM 已创建成功、回复丢失：旧业务实现补偿删除 SQL 群和成员，IM 仍保留订阅者。
- 子区 SQL 已提交、请求从未送到 IM：业务返回失败，SQL 子区仍在，IM 没有对应订阅者。

这两种情况不可能只靠 IM 内部清理队列解决。

## 实现选择

IM 保留 PR54 的持久化工作，消除重复恢复水位写入，拆开同一 Slot 的 append/apply 锁并保留 truncate 排他保护；独立数据库的 Sync 并发执行但全部完成后才确认；目标会话状态与反向关系合为同一分片批次；减少 Slot memtable/WAL 空间放大。只有已有持久化副作用和重放围栏之后的可重放 Raft applied 游标允许落盘滞后，Raft 日志、业务副作用、回执仍须同步持久化。任意回调和手动游标写入仍同步。

相邻的元数据命令按最终状态原子合并，不跨越其他命令重排。移除“至少还需 2 秒才准继续”的猜测性预算，使用实际剩余期限，不扩大原来的 5 秒。

WAL 同步窗口从 5 毫秒调整为 20 毫秒的隔离版本完成了 10 分钟及全部恢复/重启审计，零失败，成员变更最长 1.425 秒。它有明确取舍：成员增删约 112 次/秒，低于第 7 版约 210 次/秒，但高于 PR54 基线约 90 次/秒。总请求数增加主要来自消息，不能据此声称成员变更吞吐翻倍。组合版一小时已完成：25,131,544 次 HTTP 请求，零失败、零 Raft 超时；静置 121.5 秒及重启前后状态、2,555 个消息身份样本、378 个频道共 24,615,089 条消息的尾序号全部匹配。该轮成员变更平均 69.5 次/秒，最长 2.694 秒，24,491 次超过一秒；内存曾达到 4 GiB 限制并触发回收，但无 OOM。这说明这组负载下的期限目标达成，不能声称成员吞吐全面提升或仍有充足内存余量。

业务后端在修改群、成员、子区和补偿删除的同一 SQL 事务内记录脏版本。后台读取当前期望状态，提交领取事务后再访问 IM，使用持久化子区/成员分页游标和带版本、租约所有者条件的进度更新。新的业务修改会唤醒重试并使旧工作失效。

IM 通过协议 4 保留每个业务频道的版本围栏和当前页摘要：未执行过的旧快照不能覆盖新状态；已完成的精确重试可无副作用返回成功。托管频道拒绝旧式订阅增删覆盖；已经提交的过期旧命令在 Apply 中变为确定的无操作，不能卡住整个 Slot。新协议需要所有当前节点的已复制能力证明，混合版本和旧节点加入均有运行测试。

## 为什么选择这套方案，其他方案的问题在哪

这次保留两条独立边界：IM 内部解决跨分区清理的持久化和执行成本；业务数据库记录期望状态，IM 用版本拒绝过期操作。业务版本不是 Raft 超时的性能修复，它解决的是丢请求、丢回复和旧重试覆盖新状态。把这两类问题混在一起，是之前容易跑偏的地方。

| 方案 | 无法覆盖的情况 |
|---|---|
| 增大超时或一层层同步重试 | 存储成本没有下降，SQL 提交后进程崩溃仍可能丢意图 |
| 失败之后再写补偿队列 | 业务已提交、失败队列尚未写入之间的崩溃窗口 |
| 只有 SQL 队列和租约 | 租约过期的旧请求仍可能晚到 IM，覆盖重新加入 |
| 持久化排队即返回成功 | 客户端看到成功时成员和权限可能尚未生效，改变接口承诺 |
| SQL 同事务版本 + IM 版本围栏 + 有界恢复 | 覆盖上述失败窗口，但需要所有写入方协调升级，仍受实际容量限制 |

长期还可以评估子区直接继承父群订阅/权限，减少每次变更写入“成员×子区”的放大。这会改变接收标签、推送、历史和子区权限语义，需要独立设计与迁移验证。当前选择在已有语义下补齐可靠边界，并降低已定位的落盘成本。

- 一小时测试对应精确版本 636dc81b；之后只修改了迁移时删除位置的持久化。最终版本 988a5a80 必须单列后续业务及短时负载验证，不能冒用前一个二进制的测试结果。

- 启用业务版本托管前，要协调升级全部 IM 节点及业务写入方；旧业务实例不会写持久化意图。已激活数据不支持直接降级到旧协议程序。
- 无法通过新队列推断上线前已经物理删除且没有身份记录的历史孤儿；需要单独数据审计。大群快照摘要仍读取完整成员集合，不宣称任意规模常量内存。

## 额外发现：防止接管旧数据时改变会话历史

真实业务删除会话调用 UpdateConversationDeletedAtMsgSeq，保留行及删除位置。起初只看到 PreserveExisting 复制了结构体，误以为该位置一定能保留；实际回归证实通用写行函数不会写 DeletedAtMsgSeq，换行 ID 后位置从 20 变为 0。最终修复在现有原子生命周期批次中复制该字段；批量/单条路径、重启、跨分片仅一侧落盘后的断电重放均通过。未添加新协议标志，也未改变通用更新接口。

另一个直接物理删行的探针失败已保留，但它不是业务隐藏会话的调用链，不能据此宣称发现并修复了业务回归。避免把错误的前提变成新架构，是本次梳理的一部分。
